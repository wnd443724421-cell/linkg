# TC 渐进丢包与链路切换实测报告

## 1. 执行边界与方法

本轮依据用户明确授权，临时以 `netem` 替换 `wlan0` root；测试期间不保留原 `mq/fq_codel` QoS。每级结束均执行 `tc qdisc replace dev wlan0 root mq`，并验证恢复为 1 个 `mq` root + 8 个 `fq_codel` leaf。该授权偏离原任务书的“不覆盖 QoS”限制，但没有修改定版产品源码或算法阈值。

T1～T4 在 STA `wlan0` 出口单向注入，T5 在 AP/STA 两侧双向注入。每级非零丢包约 60 秒。同窗持续发送 REALTIME(UDP/14550)、摄像头 VIDEO(UDP/5600) 和 DATA(UDP/6200)，并以约 250 ms 间隔采集 AP/STA Send Plan。接收端记录逐秒包数与最大包间隙，AP `eth0` 同时保存 PCAP。

注意：脚本最后一次 `tc -s` 检查点约在注入后 55 秒，不是 60 秒清理前的最终累计值；下表丢包数量是该检查点的原始计数，丢包比例可用于核对 netem 生效，但不能冒充完整 60 秒总量。

## 6. 关键判定

1. **T1 轻微丢包无误切换。** 1% 检查点比例与配置相符，三类计划始终 Wi-Fi 主。
2. **T2 首次证明分业务迁移和 5G 用户承载。** DATA 先迁移，约 10 秒后 VIDEO 迁移，REALTIME 保留 Wi-Fi；`usb0` 的同方向大字节增量证明不是只改了策略字段。
3. **迁移顺序像 LOAD 分级，但没有直接 HCC 负载证据。** T2～T4 trace 的所有有效 `OFF` 都为 0，所有有效 `OVF` 也为 0；DATA→VIDEO→REALTIME 的分级顺序与源码 LOAD 分支一致，而 LOSS 分支按源码会让参与类一起冗余。Web 不暴露 migration_reason，因此只能标记为“疑似 TC LOSS 被快速质量组合路径按 LOAD 风格迁移”，不能直接断言内部事件名。
4. **T3/T4 在丢包仍存在时发生回 Wi-Fi 后再次迁出的振荡。** 这不是 TC 清除导致；事件均发生在 loss phase，完整计划序列保存在 JSON。
5. **T2～T4 清除 TC 后 60 秒均未自动回切。** 内部迁移原因不可见；若原因是 LOSS，RSSI 需比迁出基线高至少 3 dB；若是 LOAD，RSSI 也必须不低于迁出基线。T2 迁出时约 -38/-39 dBm，恢复观察为 -47～-49 dBm，两种门槛都不满足。场景间通过临时关闭/恢复 STA Cellular Path 复位；复位前后 `/app/linkgUser.json` SHA-256 一致。人工复位不能算自动回切通过。
6. **T5 双向全丢包最终能够切到 5G 并自动恢复。** 清除 TC 后第一次冗余验证回退到 5G，第二次才回 Wi-Fi；首次全 Wi-Fi 计划约为 27.161 秒。
7. **业务中断不满足 500 ms 参考目标。** T5 最大包间隙 DATA/VIDEO/REALTIME 分别为 1359.821/3589.581/5898.312 ms。
8. **内部 Verify/LOSS_SCORE/LOAD_SCORE/Operation ID 仍不可直接验收。** Web 只能看到计划和 PlanSync 摘要，所以本报告能证明外部状态转换与实际数据路径，不能把某个内部结果名（WIFI/CELLULAR/MIXED/INCONCLUSIVE）当作已直接观察。
9. **接口错误计数出现少量增量。** AP `usb0 rx_errors` 在 T2/T3/T5 分别增加 4/3/1，T1/T4 为 0；本轮无法仅凭 sysfs 计数唯一归因，但已保留在紧凑指标和原始 JSON，不能写成所有场景接口错误均为 0。

## 7. 清理与最终状态

五级场景均无产品源码修改。每级 qdisc 均恢复为 `mq + 8×fq_codel`；最终 AP/STA Wi-Fi 与 Cellular Path 均可用，三类计划均为 Wi-Fi single 主发、Cellular 备用；无 GStreamer、tcpdump、TC 场景脚本或 trace 临时文件残留。
